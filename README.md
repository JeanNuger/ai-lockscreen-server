# AI Lock Screen — Server

Минимальный backend для AI Lock Screen: собирает короткую анкету устройства,
раз в окно доставки (утро/день/вечер) отдаёт батч из 10 фраз + стилей,
опционально сгенерированных через OpenAI (или локальный fallback, если ключ
ещё не настроен).

Соответствует `PRODUCT_REBUILD_PLAN.md` §3–§5 (текущая версия плана в
Android-репозитории).

## Стек

- Node.js + Express
- SQLite (через `better-sqlite3`) — один файл, без отдельного сервера БД
- OpenAI Chat Completions API (не Assistants — не нужна память треда)

## Структура

```
src/
  server.js          — точка входа, health-check, монтирование роутов
  contentGenerator.js — вызов OpenAI + локальный fallback-набор фраз
  constants.js       — список из 6 style_id (должен совпадать с Android BackgroundStylePreset!)
  db/index.js        — схема SQLite, создаётся автоматически при первом запуске
  routes/
    register.js      — POST /api/v1/register (сохранение анкеты)
    batch.js          — GET  /api/v1/batch    (выдача батча фраз)
```

## Запуск локально

```bash
npm install
cp .env.example .env
# .env: оставь OPENAI_API_KEY пустым для начала — сервер будет отдавать
# локальный fallback-набор фраз, этого достаточно, чтобы проверить полный
# контракт с Android-приложением ещё до появления реального ключа.
npm start
```

Проверка:
```bash
curl http://localhost:3000/health
```

## Админ-панель

Доступна по `/admin` (редиректит на `/admin/dashboard`, если уже вошёл, иначе
на `/admin/login`). Простые статические HTML-страницы + vanilla JS — сборка
(`npm run build` и т.п.) не нужна, никакого React/Vue тут нет.

### Настройка входа

Один админ-аккаунт, без сложной системы пользователей:

```bash
node scripts/hash-password.js "твой-пароль"
```

Скопируй напечатанную строку `ADMIN_PASSWORD_HASH=...` в `.env`, добавь туда
же `ADMIN_USERNAME=твой-логин` и `SESSION_SECRET=` (любая длинная случайная
строка — например `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`).
Реальный пароль в `.env` никогда не хранится в открытом виде — только хэш.

### Разделы дашборда

- **Мониторинг** — последние 30 запросов от приложений: какое устройство,
  что отправлено в OpenAI как контекст, что получено в ответ. Обновляется
  автоматически каждые 5 секунд.
- **Устройства** — архив всех анкет (пол, возраст, интересы, цель, тон),
  с поиском.
- **Сообщения** — форма для ручной отправки фразы конкретному устройству
  или всем сразу. Сообщение **добавляется** к обычным 10 AI-фразам в
  ближайшем batch (не заменяет их) и доставляется каждому устройству ровно
  один раз (при broadcast — по одному разу на устройство, отслеживается
  отдельно для каждого).

## API

### `POST /api/v1/register`

```json
{
  "device_id": "уникальный UUID, сгенерированный на телефоне при первом запуске",
  "gender": "male | female",
  "birth_date": "YYYY-MM-DD",
  "interests": ["sport", "work", "family", "self_development"],
  "personal_goal": "строка из заранее заданных вариантов на клиенте",
  "tone": "формально | дружески | с юмором",
  "timezone": "Asia/Almaty"
}
```
Все поля кроме `device_id` опциональны. Повторный вызов с тем же `device_id`
обновляет уже сохранённые данные (upsert), не создаёт дубликат.

### `GET /api/v1/batch?device_id=...&window=morning|day|evening`

```json
{
  "phrases": [
    { "text": "Хороший день начинается с тебя", "style_id": "FOREST_GREEN" },
    ...
    (10 штук)
  ]
}
```

`style_id` — всегда одно из шести значений в `src/constants.js`
(`CLASSIC_BLUE`, `DEEP_VIOLET`, `FOREST_GREEN`, `TERRACOTTA`, `CHARCOAL`,
`SOFT_SAND`) — **обязательно должно совпадать** с именами констант в
`BackgroundStylePreset.java` на Android-стороне. Если в будущем набор
пресетов на клиенте изменится — обновить `STYLE_IDS` здесь тоже.

Устройство, ни разу не звавшее `/register`, всё равно получает батч (менее
персонализированный) — сервер не требует обязательной регистрации перед
первым запросом контента.

## Деплой на свой хостинг

Специфика зависит от того, что именно за хостинг (shared hosting с cPanel,
VPS, Docker-совместимая платформа) — общий процесс для типового
Node.js-совместимого хостинга/VPS:

1. Скопировать содержимое этого проекта на сервер (git clone или просто
   загрузка файлов, `node_modules` и `data/` не нужны — см. `.gitignore`).
2. `npm install --production` на сервере.
3. Создать `.env` на сервере (не коммитить, не пересылать по незащищённым
   каналам) — как минимум `PORT` (какой порт слушать) и, когда будет готов,
   `OPENAI_API_KEY`.
4. Настроить процесс-менеджер, чтобы сервер перезапускался при падении и
   при перезагрузке машины — например `pm2 start src/server.js --name
   ai-lockscreen-server` (если PM2 доступен), либо `systemd`-unit, если это
   VPS с полным доступом.
5. Настроить reverse proxy (обычно nginx) с HTTPS (Let's Encrypt/certbot) —
   Android-приложению нужен `https://` эндпоинт, не голый порт напрямую.
6. Проверить `https://твой-домен/health` — должен ответить `{"ok":true,...}`.

Когда решим, какой конкретно хостинг используется (shared/VPS/что-то ещё) —
можно расписать точные команды под него.

## Экономика токенов

3 запроса в сутки на устройство (не на разблокировку экрана) — см.
`PRODUCT_REBUILD_PLAN.md` §4.4. Endpoint `/batch` можно (и в проде нужно)
вызывать не чаще, чем это ограничение — сейчас сервер не рейт-лимитирует
сам, ограничение соблюдается на Android-стороне через `WorkManager` (пока
не реализовано на клиенте).

## Что дальше (не сделано в этой версии)

- Реальный `OPENAI_API_KEY` — добавить в `.env` на сервере, когда будет создан.
- Рейт-лимитинг на `/batch` (защита от случайного/злонамеренного спама
  запросов сверх 3 окон в сутки).
- Android-сторона: подключение к этому API вместо/в дополнение к
  `StaticPhraseProvider`, генерация и хранение `device_id`, три окна
  доставки через `WorkManager`.
